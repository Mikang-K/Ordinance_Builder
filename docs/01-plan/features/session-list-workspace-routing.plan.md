# 세션 목록·작업 화면 라우팅 분리 계획

- 작성일: 2026-07-28
- 상태: Planning
- 대상: `frontend`
- 구현 단계: 미착수

## 1. 배경과 문제

현재 `frontend/src/App.tsx`는 `view: 'list' | 'chat'` 로컬 상태로 세션 목록과 작업 화면을 조건부 렌더링한다. 화면은 바뀌지만 URL과 브라우저 히스토리는 바뀌지 않으므로, 작업 화면에서 브라우저 뒤로가기를 누르면 목록으로 돌아가지 않고 애플리케이션 자체를 벗어날 수 있다.

또한 현재 작업 세션 ID는 `sessionIdRef`에만 저장된다. 따라서 작업 화면을 새로고침하거나 작업 URL을 직접 열어 같은 세션을 복원하는 구조가 아니다.

## 2. 목표

- 세션 목록과 작업 화면을 서로 다른 URL을 가진 페이지로 분리한다.
- 작업 화면에서 브라우저 뒤로가기를 누르면 세션 목록으로 돌아간다.
- 브라우저 앞으로가기로 직전 작업 화면을 다시 열 수 있다.
- 작업 URL을 새로고침하거나 직접 열어도 URL의 세션 ID로 작업 상태를 복원한다.
- 인증, 세션 소유권 확인, 로딩 및 오류 처리를 라우팅 흐름과 일관되게 연결한다.

## 3. 제안 라우트

| URL | 화면 | 동작 |
| --- | --- | --- |
| `/` | 세션 목록 | 로그인한 사용자의 작업 목록 표시 |
| `/sessions/new` | 새 작업 시작 | 온보딩을 표시하고, 세션 생성 후 `/sessions/{sessionId}`로 치환 이동 |
| `/sessions/:sessionId` | 기존 작업 화면 | URL의 세션 ID로 서버 상태를 조회해 작업 복원 |
| 그 외 경로 | Not Found 또는 `/` 이동 | 잘못된 URL 처리 |

`/sessions/new`는 세션이 아직 만들어지지 않은 상태를 표현한다. 온보딩을 취소하면 `/`로 이동한다. 세션 생성 성공 후에는 `replace`를 사용해 `/sessions/new`를 실제 세션 URL로 대체하여, 뒤로가기가 다시 빈 온보딩 화면으로 돌아가지 않게 한다.

## 4. 사용자 흐름

### 새 작업

1. 목록에서 “새 조례 설계 시작” 선택
2. `/sessions/new`로 이동
3. 온보딩 입력 및 세션 생성
4. 서버에서 `session_id` 수신
5. `/sessions/{session_id}`로 `replace` 이동
6. 뒤로가기 시 `/` 목록으로 이동

### 기존 작업

1. 목록의 “계속 작성” 선택
2. `/sessions/{session_id}`로 이동
3. 작업 페이지가 `getSessionState(sessionId)` 호출
4. 응답으로 단계, 초안, 조문 큐, Q&A 내역 등을 복원
5. 뒤로가기 시 `/` 목록으로 이동

### 직접 접근 및 새로고침

1. `/sessions/{session_id}` 진입
2. 인증 확인이 끝날 때까지 세션 조회 보류
3. 인증 성공 후 세션 상태 조회
4. 세션이 없거나 접근 권한이 없으면 오류 안내와 “목록으로” 동작 제공

## 5. 구현 설계

### 5.1 라우터 도입

`react-router-dom`을 추가하고 `frontend/src/main.tsx`에서 라우터를 구성한다.

권장 컴포넌트 구조:

```text
App
├─ AuthGate
└─ Routes
   ├─ /                  -> SessionListPage
   ├─ /sessions/new      -> WorkspacePage(mode="new")
   └─ /sessions/:id      -> WorkspacePage(mode="existing")
```

Firebase Hosting에는 이미 모든 비-API 경로를 `index.html`로 보내는 rewrite가 있으므로, `/sessions/:id` 직접 접근을 위한 배포 설정 변경은 필요하지 않을 가능성이 높다. 구현 후 Hosting 프리뷰에서 이를 검증한다.

### 5.2 `App.tsx` 책임 분리

현재 `App.tsx`에 섞여 있는 책임을 다음과 같이 나눈다.

- `App.tsx`: 인증 게이트와 최상위 라우트
- `SessionListPage.tsx`: 기존 `SessionListScreen`을 조합하고 페이지 이동 처리
- `WorkspacePage.tsx`: 작업 상태, API 호출, 모달, 튜토리얼 및 작업 UI 관리
- 선택 사항 `useWorkspaceSession.ts`: 세션 초기화·복원·초기화 로직을 훅으로 추출

기존 `view`와 `setView`는 제거하고, 화면 전환은 모두 `navigate()` 또는 `<Link>`로 처리한다.

### 5.3 세션 ID를 URL 기준 상태로 전환

- 기존 세션: `useParams()`의 `sessionId`를 단일 기준으로 사용
- 새 세션: 생성 응답을 받은 즉시 실제 세션 URL로 이동
- API 요청은 현재 라우트의 세션 ID를 사용
- `sessionIdRef`는 비동기 콜백의 최신 값 보존에 꼭 필요한 경우에만 유지하고, 페이지 식별의 기준으로 사용하지 않는다.

라우트 파라미터가 바뀌면 이전 작업 상태를 초기화한 뒤 새 세션을 조회한다. 느린 이전 요청의 응답이 새 세션 화면을 덮어쓰지 않도록 effect cleanup 또는 `AbortController`/요청 식별자를 적용한다.

### 5.4 목록 이동 동작

헤더의 “목록” 버튼은 명시적으로 `navigate('/')`를 사용한다. 브라우저 뒤로가기는 히스토리에 목록이 있으면 자연스럽게 `/`로 복귀한다.

직접 URL로 작업 화면에 들어온 경우에는 이전 히스토리가 목록이 아닐 수 있으므로, 화면의 “목록” 버튼은 `navigate(-1)`이 아니라 항상 `/`로 이동해야 한다.

진행 중 편집 내용이 서버에 저장되지 않는 구간이 있다면 목록 이동 및 브라우저 이탈 전에 확인 대화상자를 표시할지 구현 전에 확인한다. 현재처럼 서버가 단계별 상태를 저장하는 범위만으로 충분하다면 별도 차단은 두지 않는다.

### 5.5 인증과 오류 처리

- 인증 확인 전에는 공통 로딩 화면 표시
- 비로그인 사용자는 기존 로그인 화면 표시
- 로그인 완료 후 원래 요청한 `/sessions/:id` 경로 유지
- 세션 조회 중에는 작업 화면 로딩 상태 표시
- 404/403은 “세션을 찾을 수 없거나 접근 권한이 없습니다”로 구분 가능한 범위에서 안내
- 오류 화면에 “목록으로”와 “다시 시도” 제공

로그아웃 시 작업 상태를 초기화하고 `/`로 `replace` 이동한다.

## 6. 예상 변경 파일

| 파일 | 변경 내용 |
| --- | --- |
| `frontend/package.json` | `react-router-dom` 의존성 추가 |
| `frontend/package-lock.json` | 잠금 파일 갱신 |
| `frontend/src/main.tsx` | 라우터 provider 구성 |
| `frontend/src/App.tsx` | 인증/라우트 중심으로 축소, `view` 상태 제거 |
| `frontend/src/pages/SessionListPage.tsx` | 목록 페이지 및 URL 이동 처리 |
| `frontend/src/pages/WorkspacePage.tsx` | 기존 작업 화면 로직 이전 및 URL 기반 세션 복원 |
| `frontend/src/components/SessionListScreen.tsx` | 콜백 또는 링크 인터페이스를 라우팅에 맞게 조정 |
| `frontend/src/App.css` | 라우트 로딩·오류 화면 스타일이 필요할 경우 추가 |
| `frontend/src/**/*.test.*` | 라우팅 및 복원 테스트 추가 |

컴포넌트 분리 범위는 구현 시 `App.tsx`의 대규모 일괄 이동을 피하도록 단계적으로 적용한다.

## 7. 구현 순서

1. 라우팅 의존성과 테스트 환경을 준비한다.
2. 현재 인증 게이트를 유지한 채 `/`, `/sessions/new`, `/sessions/:id` 라우트를 만든다.
3. 세션 목록의 새 작업/계속 작성 동작을 URL 이동으로 변경한다.
4. 작업 UI와 상태를 `WorkspacePage`로 이동한다.
5. URL 파라미터 기반 세션 조회 및 상태 복원을 구현한다.
6. 세션 생성 후 `replace` 이동, 목록 버튼, 로그아웃 이동을 정리한다.
7. 로딩·404/403·재시도 및 요청 경합 처리를 추가한다.
8. 자동 테스트와 실제 브라우저 히스토리 테스트를 수행한다.

## 8. 테스트 계획

### 자동 테스트

- `/`에서 세션 목록이 표시된다.
- 새 작업 선택 시 `/sessions/new`로 이동한다.
- 세션 생성 성공 시 `/sessions/{id}`로 치환 이동한다.
- 기존 세션 선택 시 올바른 ID의 작업 URL로 이동한다.
- `/sessions/{id}` 직접 진입 시 해당 세션 API를 호출하고 상태를 복원한다.
- 세션 ID가 바뀌면 이전 상태가 초기화되고 새 세션이 로드된다.
- 잘못된/권한 없는 세션은 오류 화면을 표시한다.
- 로그아웃 후 보호된 작업 화면이 남지 않는다.

테스트 도구가 현재 없으므로 Vitest, React Testing Library, 메모리 라우터 도입을 함께 검토한다. 의존성 추가 범위를 최소화해야 한다면 우선 빌드 검사와 브라우저 시나리오 테스트로 시작하고, 라우팅 회귀 방지를 위해 후속 자동 테스트를 반드시 등록한다.

### 브라우저 수동 검증

- 목록 → 새 작업 → 작업 화면 → 뒤로가기 → 목록
- 목록 → 기존 작업 → 뒤로가기 → 목록 → 앞으로가기 → 같은 작업
- 작업 URL 새로고침 후 상태 복원
- 작업 URL을 새 탭에 붙여넣어 직접 접근
- `/sessions/new`에서 온보딩 취소
- 존재하지 않는 세션 ID 및 다른 사용자의 세션 ID 접근
- 모바일 브라우저의 시스템 뒤로가기
- Firebase Hosting 프리뷰에서 하위 경로 직접 접근

## 9. 완료 기준

- 목록과 작업 화면의 URL이 실제로 분리되어 있다.
- `view` 상태 없이 라우트가 현재 화면을 결정한다.
- 정상적인 목록 진입 후 작업 화면에서 브라우저 뒤로가기를 누르면 목록이 보인다.
- 작업 URL의 새로고침·직접 접근·앞으로가기가 동일 세션을 복원한다.
- 새 세션 생성 후 히스토리에 불필요한 `/sessions/new` 항목이 남지 않는다.
- 인증 및 세션 오류에서 앱이 빈 화면이나 무한 로딩에 빠지지 않는다.
- `npm run build`가 통과한다.
- 위 브라우저 시나리오가 Firebase Hosting과 동일한 rewrite 환경에서 통과한다.
