# 조례 문서 통합 작업공간 및 재작성 흐름 구현 계획

## 1. 목적

상세 조례, 조례 초안, 확정 조례를 별도 모달이나 단계별 임시 화면이 아닌 하나의 작업공간에 배치한다. 사용자는 탭으로 각 문서를 자유롭게 확인하고, 이전 단계의 내용을 수정해 새 초안과 확정본을 다시 만들 수 있어야 한다.

핵심 원칙은 다음과 같다.

- 탭 이동은 조회 동작이며 서버 데이터를 변경하지 않는다.
- 이전 단계 수정은 명시적인 적용 동작을 거쳐야 한다.
- 이전 단계가 바뀌면 그 내용을 기반으로 만든 후속 결과는 자동으로 재사용하지 않는다.
- 기존 확정본은 보존하고, 수정 작업은 새 개정본으로 관리한다.
- 새 개정본은 법률 검토를 다시 통과해야 확정할 수 있다.

## 2. 현재 구조와 해결할 문제

현재 프런트엔드의 작업공간 탭은 `상세 조례`와 `조례 초안`만 지원한다. `확정 조례`는 별도의 `CompletedDraftModal`로 열리며, 완료 단계에서는 상세 조례 탭의 접근 조건도 현재 워크플로 단계에 묶여 있다.

백엔드 워크플로는 상세 입력 → 초안 → 법률 검토 → 완료의 순방향 전이를 전제로 한다. 완료 후 이전 단계로 돌아가 내용을 수정하고 후속 결과를 다시 생성하는 명시적 상태 전이나 개정 버전 모델은 없다.

따라서 UI 탭만 추가하면 다음 문제가 남는다.

- 완료된 세션에서 상세 조례를 다시 열 수 없음
- 이전 입력 수정 후 기존 초안·법률 검토·확정본의 유효성 판단이 불명확함
- 수정 도중 새로고침하면 편집 상태가 유실될 수 있음
- 기존 확정본이 수정본으로 덮어써져 복구와 감사 추적이 어려움

## 3. 목표 사용자 흐름

### 3.1 작업공간 탭

작업공간 상단에 다음 세 탭을 항상 같은 위치에 표시한다.

1. `상세 조례`
2. `조례 초안`
3. `확정 조례`

각 탭에는 상태를 함께 표시한다.

- 작성 중
- 변경됨
- 생성 필요
- 법률 검토 필요
- 검토 완료
- 확정

아직 데이터가 없는 탭은 숨기지 않고 비활성화하며, 활성화 조건을 짧게 안내한다. 데이터가 한 번 생성된 탭은 현재 워크플로 단계와 관계없이 계속 조회할 수 있어야 한다.

### 3.2 탭 이동

- 탭 선택만으로는 저장, 재생성, 확정 상태 변경을 실행하지 않는다.
- 선택한 탭은 URL의 세션 경로에 쿼리 값으로 반영한다. 예: `/sessions/{id}?tab=draft`
- 새로고침이나 브라우저 뒤로 가기 후에도 같은 세션과 탭이 복원된다.
- 편집 중 저장하지 않은 변경이 있으면 다른 탭으로 이동하기 전에 `변경사항 유지`, `변경 취소`, `계속 편집` 중 적절한 선택을 제공한다.

### 3.3 이전 단계 재작성

#### 상세 조례 수정

1. 사용자가 상세 조례 탭에서 내용을 편집한다.
2. 화면에는 아직 반영되지 않은 변경임을 표시한다.
3. `변경사항 적용 및 초안 다시 만들기`를 누른다.
4. 기존 확정본에 미치는 영향을 안내하고 확인을 받는다.
5. 서버가 새 개정본을 만들고 수정된 상세 데이터를 저장한다.
6. 새 개정본의 기존 초안, 법률 검토 결과, 확정 상태를 무효화한다.
7. 초안을 다시 생성한 뒤 조례 초안 탭으로 이동한다.

#### 조례 초안 수정

1. 사용자가 조례 초안 탭에서 문안을 편집한다.
2. `변경사항 저장`으로 새 개정본의 초안을 저장한다.
3. 기존 법률 검토 결과와 확정 상태를 무효화한다.
4. `법률 검토`를 다시 실행한다.
5. 검토가 끝나야 `확정 조례로 확정` 버튼이 활성화된다.

#### 확정 조례 확인

- 확정 조례 탭은 읽기 전용으로 제공한다.
- 복사, TXT, DOCX 내보내기 기능을 유지한다.
- 새 개정 작업 중에도 직전 확정본을 `현재 확정본`으로 조회하고 내보낼 수 있다.
- 새 개정본이 다시 확정되면 이전 확정본은 이력으로 보존한다.

## 4. 상태 및 버전 모델

덮어쓰기 방식보다 세션 안에 개정 버전을 두는 방식을 권장한다.

### 4.1 개정 데이터

개정본마다 최소한 다음 정보를 저장한다.

- `revision_id`
- `revision_number`
- `status`: `editing_articles`, `drafting`, `editing_draft`, `legal_reviewing`, `ready_to_finalize`, `completed`
- `article_contents`
- `draft_full_text`
- `legal_issues`
- `legal_reviewed_at`
- `finalized_at`
- `created_at`, `updated_at`
- `based_on_revision_id`
- 동시 수정 검사를 위한 `version` 또는 `updated_at`

세션에는 다음 포인터를 둔다.

- `active_revision_id`: 현재 편집 중인 개정본
- `finalized_revision_id`: 사용자에게 현재 확정본으로 제공할 개정본

초기 구현에서는 기존 체크포인트 상태를 유지하되, 개정 메타데이터와 문서 스냅샷을 별도 저장하는 어댑터 계층을 두어 점진적으로 이전한다.

### 4.2 후속 결과 무효화 규칙

| 변경 대상 | 유지 | 무효화 및 재실행 |
| --- | --- | --- |
| 상세 조례 | 기존 확정본 이력 | 초안, 법률 검토, 새 확정 상태 |
| 조례 초안 | 상세 조례, 기존 확정본 이력 | 법률 검토, 새 확정 상태 |
| 법률 검토 재실행 | 상세 조례, 초안 | 이전 검토 결과 |
| 확정 | 현재 개정본 전체 | 없음 |

기존 확정본은 수정으로 삭제하거나 변경하지 않는다.

## 5. 프런트엔드 구현

### 5.1 작업공간 셸

`App.tsx`에 흩어진 모달 열림 상태를 문서 작업공간 상태로 통합한다.

- `workspaceTab` 타입을 `articles | draft | final`로 확장
- 탭 활성화 여부를 현재 `stage`가 아니라 서버가 반환한 문서 가용성과 개정 상태로 계산
- 완료 세션 복원 시 모달을 자동으로 띄우지 않고 `final` 탭을 선택
- 헤더의 상세/초안/확정 관련 동작은 모달을 여는 대신 해당 탭으로 이동
- 비동기 생성·검토 중에는 현재 요청의 개정 번호를 확인해 오래된 응답이 최신 편집 내용을 덮지 못하게 처리

### 5.2 컴포넌트 정리

- `ArticleItemsModal`의 편집 본문을 `ArticleWorkspacePanel`로 분리하거나 기존 `embedded` 모드를 작업공간 전용으로 정리
- `DraftModal`의 본문을 `DraftWorkspacePanel`로 분리하고 저장되지 않은 변경 상태를 상위에 전달
- `CompletedDraftModal`을 `FinalOrdinancePanel`과 모달 셸로 분리
- 공통 `WorkspaceDocumentTabs` 컴포넌트에서 탭, 상태 배지, 비활성 사유, 키보드 탐색을 담당
- 각 패널은 문서 데이터와 편집 콜백만 받고 세션 전환 로직은 작업공간 컨테이너가 담당

### 5.3 편집 UX

- 상세 및 초안 편집 시 상단 또는 하단 고정 영역에 저장 상태를 표시
- `저장됨`, `저장 중`, `저장되지 않음`, `저장 실패` 상태를 시각적으로 구분
- 이전 단계 변경 적용 전에 영향 범위를 구체적으로 안내
- 생성 및 법률 검토 중에도 다른 탭의 읽기는 허용하되, 중복 제출 버튼은 잠금
- 오류 발생 시 편집 내용을 브라우저 메모리 또는 안전한 로컬 임시 저장소에 유지
- 탭은 WAI-ARIA tab 패턴을 적용하고 좌우 방향키, Home, End 이동을 지원
- 모바일에서는 탭을 가로 스크롤하거나 짧은 라벨을 사용하되 문서 순서는 유지

## 6. 백엔드 구현

### 6.1 조회 응답 확장

세션 상태 응답에 다음 값을 추가한다.

- 활성/확정 개정 메타데이터
- 저장된 상세 조례 입력 전체
- 활성 개정본 초안과 법률 검토 결과
- 현재 확정본 스냅샷
- 탭별 조회·편집 가능 여부
- 후속 재생성이 필요한 이유

프런트엔드가 `current_stage`를 해석해 탭 상태를 추측하지 않도록 서버가 명시적인 문서 상태를 반환한다.

### 6.2 API 계획

구체적인 경로는 기존 라우터 규칙에 맞추되 책임은 다음과 같이 분리한다.

- `GET /session/{id}/workspace`: 세 탭의 데이터와 개정 상태 조회
- `PATCH /session/{id}/revisions/{revision_id}/articles`: 상세 조례 임시 저장
- `POST /session/{id}/revisions/from-articles`: 상세 변경을 기반으로 새 개정본 생성 및 초안 재생성
- `PATCH /session/{id}/revisions/{revision_id}/draft`: 초안 저장 및 검토 결과 무효화
- `POST /session/{id}/revisions/{revision_id}/legal-review`: 현재 초안 재검토
- `POST /session/{id}/revisions/{revision_id}/finalize`: 검토 완료된 현재 개정본 확정
- `GET /session/{id}/revisions`: 확정 이력 조회

변경 API는 `expected_version`을 받아 오래된 화면의 저장 요청에는 `409 Conflict`를 반환한다.

### 6.3 워크플로 전이

- 완료 상태에서 기존 그래프 상태를 직접 과거 단계로 덮어쓰지 않는다.
- 상세 변경 적용 시 새 개정 체크포인트를 생성하고 `drafting`부터 실행한다.
- 초안 변경 시 활성 개정본을 `editing_draft`로 전환하고 법률 검토 결과를 제거한다.
- 확정 API는 현재 개정본의 최근 법률 검토가 현재 초안 해시와 일치할 때만 성공한다.
- 생성·검토·확정 요청에는 멱등성 키를 적용해 중복 클릭과 재시도로 인한 중복 개정본을 방지한다.

## 8. 구현 순서

### 1단계: 계약과 상태 모델

- 개정본 및 탭 상태 스키마 정의
- 후속 결과 무효화 규칙과 API 오류 계약 확정
- 기존 완료 세션의 호환·마이그레이션 정책 정의

완료 기준: 동일한 세션에서 현재 편집본과 현재 확정본을 동시에 표현할 수 있다.

### 2단계: 백엔드 개정 흐름

- 작업공간 조회 API 구현
- 상세/초안 저장 및 새 개정 생성 구현
- 법률 검토와 확정의 개정 일치 검증 구현
- 동시 수정 및 중복 요청 방어 구현

완료 기준: 완료 세션의 확정본을 보존한 채 상세 조례 또는 초안을 수정해 새 확정본을 만들 수 있다.

### 3단계: 통합 작업공간 UI

- 세 탭과 상태 배지 구현
- 기존 세 모달의 콘텐츠를 작업공간 패널로 통합
- URL 탭 복원, 로딩, 빈 상태, 오류 상태 구현
- 헤더 액션을 탭 이동 방식으로 변경

완료 기준: 모든 문서가 같은 위치에서 전환되고 별도 완료 모달이 필요하지 않다.

### 4단계: 재작성 UX

- 변경 감지와 미저장 이동 방지
- 영향 확인 다이얼로그
- 재생성·재검토 진행 상태와 실패 복구
- 이전 확정본 조회 및 내보내기 유지

완료 기준: 사용자가 수정의 영향과 현재 저장 상태를 항상 알 수 있다.

### 5단계: 검증과 배포 준비

- 단위·통합·브라우저 테스트
- 기존 세션 데이터 호환 테스트
- 접근성 및 반응형 검증
- 운영 마이그레이션과 롤백 절차 작성

완료 기준: 테스트·리뷰 산출물이 준비되고 배포 승인 전 단계에 도달한다.

## 9. 테스트 계획

### 프런트엔드

- 단계별 탭 활성화와 상태 배지
- 완료 세션을 열 때 확정 조례 탭 표시
- URL로 특정 탭 직접 진입 및 뒤로/앞으로 이동
- 미저장 상태에서 탭 이동, 세션 이동, 새로고침 방지
- 상세 변경 후 초안 재생성 결과 표시
- 초안 변경 후 법률 검토 전 확정 버튼 비활성화
- 생성/검토 중 중복 제출 방지
- 복사 및 TXT/DOCX 내보내기 회귀 테스트
- 키보드 탭 탐색과 스크린 리더 레이블
- 좁은 화면에서 탭과 편집 영역 레이아웃

### 백엔드

- 기존 완료 세션에서 새 개정 생성
- 상세 변경 시 후속 데이터 무효화
- 초안 변경 시 기존 법률 검토 무효화
- 검토하지 않은 초안의 확정 거부
- 다른 초안 해시로 받은 과거 검토 결과의 확정 거부
- `expected_version` 충돌 시 409 반환
- 멱등성 키 재요청 시 중복 개정 미생성
- 기존 확정본 스냅샷 불변성
- 권한 없는 세션·개정 접근 거부

### 핵심 시나리오

1. 조례를 작성하고 법률 검토 후 확정한다.
2. 확정 조례 탭에서 내보내기가 정상 동작하는지 확인한다.
3. 상세 조례 탭으로 돌아가 한 항목을 수정한다.
4. 영향 안내를 확인하고 새 초안을 생성한다.
5. 이전 확정본이 그대로 조회되는지 확인한다.
6. 새 초안을 편집하고 법률 검토를 다시 실행한다.
7. 새 버전을 확정하고 확정 이력과 현재 확정본이 올바른지 확인한다.

## 10. 수용 기준

- 상세 조례, 조례 초안, 확정 조례가 동일한 작업공간의 세 탭으로 제공된다.
- 완료된 세션에서도 상세 조례와 초안을 다시 조회할 수 있다.
- 탭 이동만으로 서버 상태나 문서가 변경되지 않는다.
- 이전 단계 편집 시 영향을 받는 후속 결과를 사용자에게 명확히 알린다.
- 상세 조례를 바꾸면 초안과 법률 검토를 다시 수행해야 한다.
- 조례 초안을 바꾸면 법률 검토를 다시 수행해야 한다.
- 법률 검토가 현재 초안과 일치하지 않으면 확정할 수 없다.
- 기존 확정본은 새 개정 작업 중에도 보존되고 내보낼 수 있다.
- 새로고침과 브라우저 뒤로 가기 후 세션과 선택 탭이 복원된다.
- 미저장 변경, 요청 실패, 동시 편집 충돌에서 사용자 입력이 조용히 유실되지 않는다.
- 데스크톱과 모바일에서 탭 및 주요 작업 버튼이 겹치거나 잘리지 않는다.

## 11. 범위 제외

초기 구현에서는 다음 기능을 제외한다.

- 두 개정본의 문장 단위 비교 화면
- 여러 사용자의 실시간 공동 편집
- 개정본 병합
- 관리자용 전사 감사 대시보드
- 자동 확정 또는 법률 검토 생략

개정 이력 데이터는 처음부터 보존하되, 비교 UI는 후속 단계로 분리한다.

## 12. 주요 위험과 대응

- 기존 체크포인트가 개정 분기를 지원하지 않을 수 있음: 개정 메타데이터와 스냅샷을 별도 서비스로 분리하고 그래프 실행 입력을 명시적으로 구성한다.
- 완료 세션 호환성 문제: 기존 세션을 최초 조회할 때 현재 상태를 개정 1로 투영하는 읽기 호환 계층을 둔다.
- 오래 걸리는 생성 응답이 최신 편집을 덮을 수 있음: 모든 비동기 결과에 `revision_id`와 `version` 검사를 적용한다.
- 법률 검토와 초안 불일치: 초안 해시를 검토 결과에 저장하고 확정 시 서버에서 재검증한다.
- 편집 상태가 여러 컴포넌트에 분산될 수 있음: 작업공간 컨테이너를 단일 조정 지점으로 두고 패널은 표시와 입력에 집중한다.
